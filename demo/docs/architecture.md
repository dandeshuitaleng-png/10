# Day 1工程框架与接口边界

目标：直接复用微信原生Canvas2D运行环境，组织后续四选一知识闯关开发；不迁移到Unity/其他引擎，不保留飞机大战业务。

## 模块和数据流

`game.js → App → WeChatPlatform / Router / Input / Resources / Renderer`

输入先转换为375逻辑宽度的坐标；按下目标后，移动超出阈值、滑出或取消均不触发。每次绘制只注册本画面的有效目标；复活模态独占触摸。Canvas按设备像素比设置实际尺寸，逻辑位置根据窗口宽高、安全区及胶囊底部计算，顶部至少避让44个物理像素。

启动展示动画加载进度；两张图片完成或失败后进入首页。资源失败保留原生符号回退，失败资源留在`Resources.failures`供后续上报。切后台停止绘制与音频、取消按压；返回后重算窗口，保留当前页面；销毁时移除监听。

当前可运行路径：启动→首页→主题地图→本关题目准备页→返回。榜单和证书入口有准备/说明页，不生成虚假排名与证书。

四主题首关可点只是Day 1导航样板，尚无正式挑战记录或跨主题开放策略。节点解锁、当日锁定和重玩权限必须在正式挑战实现时根据可信记录与确认后的规则计算，不能直接继承样板的0/4、固定首关状态。

## 后续后端接口契约草案

以下是预留接口，不表示后台已存在；使用注入的transport接入正式服务。实际域名、身份鉴别和请求格式待工程联调确定。

| 操作 | 输入 | 正式接入时必须核实 |
| --- | --- | --- |
| challenge.begin | levelId | 关卡开放/锁定、可信日期、题库版本、10题题序、单题时限与挑战ID |
| challenge.answer | challengeId、questionId、optionId | 服务端判定、单次提交、进度、错误/复活状态和版本一致 |
| challenge.revive | challengeId、verifiedEvidence | 服务端验证分享依据、1次额度、恢复当前题；不能凭返回前台或客户端布尔值发放 |
| ranking.list | day/total | 通关关数优先、正确率其次；统计口径和并列规则按确认结果 |
| certificates.list | 当前身份上下文 | 单主题4关/全部16关完成条件、重复请求、展示与保存策略 |

未配置transport时返回明确错误，不制造成功响应。正式挑战、积分、锁定和证书不能只信任客户端；目前Storage只存静音偏好，不存伪造积分或通关记录。

## 题库与管理端后续工作

正式题池现在为空；不足10题不能开始正式挑战。后续题目需要唯一ID、主题/关卡、题干、4选项、唯一正确答案、解析、基础/进阶/综合标签及需要的媒体。

基础、关卡、题库、复活、积分五项管理模块按既定计划接入。这次不搭假管理后台，不以接口文件代替后台可用。

待定规则保留null：单题时长、超时处理、复活额度周期、日界线、正确率口径、重玩积分与分享验证条件。分享接口若不能支撑原需求，先向用户报告平台验证结果，不自行更改奖励条件。

## 接口参考与证据

平台接口按[微信团队官方小游戏API类型库](https://github.com/wechat-miniprogram/minigame-api-typings)核对；项目原配置和原生入口同时保留。官方文档页面本轮读取失败，包过滤配置及实际API行为仍须在微信开发者工具检查。不将类型声明、宿主模拟或源代码存在当作真机通过。

## 连续十题试玩

`core/challenge.js`提供本地试玩状态机，`data/practice.js`提供12道示例题。正式题池仍为空。`main.js`将试玩状态传给原Renderer；`design/play.html`提供浏览器平台适配，复用同一流程。正式评分必须使用服务端，不能把本地答案、成绩或注入的`verified:true`当作可信平台证据。正式日锁定和解锁存档尚未接入；本地状态机的locked仅代表当前挑战状态，没有自行规定日期边界。
